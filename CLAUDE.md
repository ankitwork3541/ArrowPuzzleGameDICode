## What This Project Is

A 2D Unity arrow-path puzzle game targeting **50,000+ levels**. Mechanic: arrows sit on a grid as a chain of cells; tapping an arrow slides it forward one cell in its head's direction (like a snake), continuing automatically until it either exits the board (path clear all the way off-grid) or blocks (another arrow in the way — bumps forward slightly, flashes red, reverses back). Full product-level detail lives in `Docs/Game-Design.md`.

## Architecture Decisions (PLANNED — nothing below this line exists in code yet, see reset notice above)

- **New Input System** (`UnityEngine.InputSystem`) for all of the user's own scripts.
- **Hybrid rendering**: `LineRenderer` (+ `EdgeCollider2D`) for the arrow body (smooth, gap-free, native rounded corners via `numCornerVertices`), with separate hand-drawn sprite objects for the head and tail riding the line's ends. Full rationale in `Docs/Game-Design.md` §3.
- **Click detection**: one check per arrow (New Input System), not per body segment.
- **Data-driven levels**: grid dimensions + arrow paths as data (ScriptableObject and/or JSON — exact format TBD when we rebuild level loading).
- **Multi-theme from the start**: whatever renders an arrow's look (body width/color, head/tail sprite) needs to be swappable data, not hardcoded.
- **50,000+ levels**: hybrid generation — procedural (reverse-construction technique, guarantees solvability by construction) + manual hand-crafted levels, with a solvability checker mandatory for manual ones. Not started.
- **Object pooling**: deferred until many levels are actually being cycled through in testing. Now being picked up for the grid background dots (see below) since Huge level (~1500 cells) is a concrete trigger.
- **Grid background dots** (decided 2026-08-09, after web research comparing per-cell GameObject vs. shader-based single quad vs. Unity Tilemap): **per-cell `Dot` GameObject** (`SpriteRenderer`), one per empty grid cell — matches the MultiTech template's `Dot.cs`/`GridManager.cs` concept. Shader-based and Tilemap approaches were rejected: at ~1500 cells URP's SRP Batcher already makes per-object sprites cheap, and both alternatives would still need pooled GameObjects for the per-cell pop-reveal animation anyway (see below), so they'd add a second rendering system without removing the pooling work. Dots are pooled via Unity's built-in `UnityEngine.Pool.ObjectPool<T>`, not a hand-rolled pool. When an arrow's tail vacates a cell, that cell's dot plays a one-shot "pop" reveal (scale `0 → overshoot → 1`), timed to the arrow's per-cell step speed.
- **Tweening**: **PrimeTween** (zero-allocation, struct-based) is now the ONLY tween library used by `Assets/Project` code — chosen over DOTween (Asset Store plugin, `Assets/Plugins/Demigiant`, still installed but unused) because DOTween allocates GC per tween/delay, which would show up as periodic GC-spike jank with many simultaneous short pop-tweens at scale (1500-cell grids, many arrows animating at once). Adopted first for the dot pop-reveal and Hint pulse (new code), then `ArrowController`'s move/block/exit tweens were migrated too (2026-08-09) — full migration done, not partial as originally planned (`git-URL` package, `https://github.com/KyryloKuzyk/PrimeTween.git`).

## Script Folder Structure

`Assets/Project/Scripts/` has these subfolders (created before the reset, kept empty until now) — put every new script in the matching one so the project stays organized as it grows:

- **`Core/`** — core gameplay logic: grid system, movement, blocking/exit logic (e.g. `GridCell.cs`, `GridBuilder.cs`). Plain data classes and MonoBehaviours that drive the actual game mechanic live here.
- **`Data/`** — data models: `ScriptableObject` classes and `[System.Serializable]` plain classes that hold level/theme/config data (e.g. `LevelData.cs`, `ArrowPathData.cs`).
- **`Managers/`** — manager-style MonoBehaviours that coordinate systems across the scene (e.g. a future `LevelManager`, `GameManager`) — not used yet.
- **`UI/`** — scripts driving UI elements (hearts/lives display, hint button, score/level text, and as of 2026-08-11 the UI Toolkit controllers like `SplashScreenController.cs`).
- **`Utils/`** — generic reusable helpers not tied to this game's specific mechanic (e.g. `CanvasScalerAutoFit.cs`).

Other relevant top-level folders: `Assets/Project/Prefabs/`, `Assets/Project/Levels/` (for saved `LevelData` assets), `Assets/Project/Sprites/`, `Assets/Project/Scenes/` (contains `Game.unity`).

**UI Toolkit asset folders** (added 2026-08-11, for the §11b UI Toolkit rebuild): non-script UI Toolkit assets get their own top-level folders, siblings of `Scripts/`/`Sprites/`/etc., not nested under `Scripts/UI/` (which is for `.cs` files only):
- **`Assets/Project/UXML/`** — every `.uxml` document (`SplashScreen.uxml`, `HomeScreen.uxml`, etc.) and the shared `MainPanelSettings.asset` (`PanelSettings`, the UI Toolkit equivalent of `CanvasScaler`) — small number of infra assets, kept together rather than fragmented into more folders.
- **`Assets/Project/Themes/`** — every `.uss` stylesheet (`SplashScreen.uss`, etc.) — this folder already existed before the UI Toolkit work started; USS files fit its name well (Unity's own terminology calls a full USS-driven look a "theme").

Moving an already-referenced Unity asset (e.g. reorganizing folders later) must move its paired `.meta` file alongside it (matching filename + `.meta`) — Unity's asset references are GUID-based via the `.meta` file, not path-based, so this keeps every existing scene/component reference intact with zero re-wiring. - **2026-08-07 — Fixed a real corner-animation bug in `MoveStep`/`ExitStepOnce`: bent arrows showed a diagonal "cut" while passing through a turn.** Root cause: both methods animated by shifting the whole points array and `Vector3.Lerp`-ing each index independently from its old to new position (`to[i] = from[i+1]`) — mathematically, when two adjacent points move in *different* directions simultaneously (a turn), the segment between their interpolated positions sweeps diagonally for the duration of the tween. Confirmed this is inherent to that technique (proved it algebraically, and the MultiTech template's `ArrowLine.StepOnce()` uses the identical `Lerp(from[i], to[i], t)` pattern) — visible in the template too, just camouflaged by thin lines/fast speed/small grid units, not something we could copy our way out of. **Real fix**: rewrote both methods with a "head grows, tail shrinks, middle freezes" technique (how real snake games do it) — all interior/corner points are set once and never touched again during a step; only the tail (sliding toward its old neighbor, always along that neighbor's existing straight direction) and the head (growing from the old head toward the new one, always along the current head direction) animate, each in a single straight line, so no two connected points ever move in different directions at once.
