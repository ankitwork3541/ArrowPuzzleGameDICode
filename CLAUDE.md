## What This Project Is

A 2D Unity arrow-path puzzle game targeting **50,000+ levels**. Mechanic: arrows sit on a grid as a chain of cells; tapping an arrow slides it forward one cell in its head's direction (like a snake), continuing automatically until it either exits the board (path clear all the way off-grid) or blocks (another arrow in the way — bumps forward slightly, flashes red, reverses back). Full product-level detail lives in `Docs/Game-Design.md`.

## Architecture Decisions (PLANNED — nothing below this line exists in code yet, see reset notice above)

- **New Input System** (`UnityEngine.InputSystem`) for all of the user's own scripts.
- **Hybrid rendering**: `LineRenderer` (+ `EdgeCollider2D`) for the arrow body (smooth, gap-free, native rounded corners via `numCornerVertices`), with separate hand-drawn sprite objects for the head and tail riding the line's ends. Full rationale in `Docs/Game-Design.md` §3.
- **Click detection**: one check per arrow (New Input System), not per body segment.
- **Data-driven levels**: grid dimensions + arrow paths as data (ScriptableObject and/or JSON — exact format TBD when we rebuild level loading).
- **Multi-theme from the start**: whatever renders an arrow's look (body width/color, head/tail sprite) needs to be swappable data, not hardcoded.
- **50,000+ levels**: hybrid generation — procedural (reverse-construction technique, guarantees solvability by construction) + manual hand-crafted levels, with a solvability checker mandatory for manual ones. Not started.
- **Object pooling**: deferred until many levels are actually being cycled through in testing. Now being picked up for the grid background dots (see below) since Huge level (~1500 cells) is a concrete trigger.
- **Grid background dots** (decided 2026-08-09, after web research comparing per-cell GameObject vs. shader-based single quad vs. Unity Tilemap): **per-cell `Dot` GameObject** (`SpriteRenderer`), one per empty grid cell — matches the MultiTech template's `Dot.cs`/`GridManager.cs` concept. Shader-based and Tilemap approaches were rejected: at ~1500 cells URP's SRP Batcher already makes per-object sprites cheap, and both alternatives would still need pooled GameObjects for the per-cell pop-reveal animation anyway (see below), so they'd add a second rendering system without removing the pooling work. Dots are pooled via Unity's built-in `UnityEngine.Pool.ObjectPool<T>`, not a hand-rolled pool. When an arrow's tail vacates a cell, that cell's dot plays a one-shot "pop" reveal (scale `0 → overshoot → 1`), timed to the arrow's per-cell step speed.
- **Tweening**: adopting **PrimeTween** (zero-allocation, struct-based) for new tween code going forward, starting with the dot pop-reveal animation — chosen over continuing with DOTween (Asset Store plugin, `Assets/Plugins/Demigiant`, already used for arrow movement) because DOTween allocates GC per tween/delay, which would show up as periodic GC-spike jank with many simultaneous short pop-tweens at scale (1500-cell grids, many arrows animating at once). **Plan: existing DOTween usage (`ArrowController` moves) migrates to PrimeTween gradually, later** — not a big-bang rewrite. Not yet installed (git-URL package, `https://github.com/KyryloKuzyk/PrimeTween.git`).

- **2026-08-07 — Procedural generator's reverse-construction guarantee had a real solvability hole — fixed and verified with 4 generated levels, all fully solved by hand.** `IsExitClear()` only checked a new arrow's exit ray against `occupied` (other, earlier-placed arrows) — never against the *walk's own cells*. A random walk can curl into a hook/loop shape where the head's exit ray, extended forward, re-enters a cell that's part of its own earlier body — that arrow is then permanently self-blocked (its own tail occupies the cell its head needs, and the tail can't vacate until the head passes, which it never can) — a silent solvability hole despite the reverse-construction logic itself being sound (re-verified the placement/solve-order proof by hand: solve order = exact reverse of placement order, each arrow's exit-clear check at placement time exactly matches what it needs at its solve moment, since arrows solved *after* it in reverse order are still present with unchanged occupancy, and arrows solved *before* it have already exited by the time it's checked — the gap was purely the missing self-collision check, not the ordering logic). - **2026-08-07 — Fixed a real corner-animation bug in `MoveStep`/`ExitStepOnce`: bent arrows showed a diagonal "cut" while passing through a turn.** Root cause: both methods animated by shifting the whole points array and `Vector3.Lerp`-ing each index independently from its old to new position (`to[i] = from[i+1]`) — mathematically, when two adjacent points move in *different* directions simultaneously (a turn), the segment between their interpolated positions sweeps diagonally for the duration of the tween. Confirmed this is inherent to that technique (proved it algebraically, and the MultiTech template's `ArrowLine.StepOnce()` uses the identical `Lerp(from[i], to[i], t)` pattern) — visible in the template too, just camouflaged by thin lines/fast speed/small grid units, not something we could copy our way out of. **Real fix**: rewrote both methods with a "head grows, tail shrinks, middle freezes" technique (how real snake games do it) — all interior/corner points are set once and never touched again during a step; only the tail (sliding toward its old neighbor, always along that neighbor's existing straight direction) and the head (growing from the old head toward the new one, always along the current head direction) animate, each in a single straight line, so no two connected points ever move in different directions at once. Line temporarily grows to `n+1` points during the tween (`[shrinking tail, frozen middle..., growing head]`), collapses back to `n` in `OnComplete`. User caught a real gap while debugging: the fix initially only went into `MoveStep`, but `ExitStepOnce` still had the old flawed algorithm and could still show the diagonal on a bend that's still present when exit starts — fixed there too, same technique.
